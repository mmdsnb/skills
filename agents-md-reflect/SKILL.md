# AGENTS.md 反映

项目开始时写的 AGENTS.md 是初稿；真正的规则藏在会话里——用户反复纠正、重复交代、以为 agent 该懂却每次都要说的东西。这个 skill 把两者对齐，让用户看完说「原来我一直在干这个」。

## 取材料

脚本只读用户消息，本地处理，不外发。

```sh
python3 "<skill_dir>/scripts/history.py" --project . --source all --out /tmp/agents-history.txt
```

- `--source all` 同时读 qoder 与 opencode；`--days 90` 限时间；默认全量。
- 输出已按原文去重，`xN` 表示同一句话在历史里出现过 N 次。
- 当前 AGENTS.md 在项目根目录；初始版在 git 里：`git log --follow --format='%h %ad %s' --date=short -- AGENTS.md`，需要时 `git show <最早提交>:AGENTS.md`。

## 找什么

不是找抱怨，是找重复 ≥2 次的结构性要求：

- 反复纠正：「不要…」「我说的是…」「你怎么又…」
- 反复交代的约定：路径、命名、测试、提交、输出格式、语言
- 口径变化：先说可以、后来禁止；先要求测试、后来允许瑕疵
- 收尾时才说的真实标准：「我要的是…」往往定义了他真正的验收

一次性的任务指令不算规则。

## 对比成三类

对着当前 AGENTS.md 逐条判断，每条都带原话和时间：

| 类型 | 判据 |
| --- | --- |
| 该写没写 | 反复出现，文件里没有 |
| 写了没守 | 文件里有，但会话里仍在纠正 → 规则不可执行或已过时 |
| 前后矛盾 | 两条规则或两个时期的诉求冲突 |

## 输出

1. 先给一句结论：「你一直在…」，必须能被用户用「对，就是这个」确认。
2. 最多 5 条差异，按重复次数排序；每条：原话（带日期）→ 现状 → 建议怎么写。
3. 推断明确标「推断」；证据不足就说没有稳定模式，不硬凑。
4. 用户确认哪些条目后，才改 AGENTS.md；规则写成「触发条件 + 动作 + 边界」，不写「要重视」。

## 写回

- 改前确认 `git status`，不覆盖未提交的改动。
- 不自动 commit；用户要求时再按仓库约定提交。
- 若用户有 AGENTS.md 备份约定（如 Obsidian 的 `30 Resources/32 AGENTS.md 备份/`），写完整份原文。

## 验收

用户看完说「对，我一直在干这个」，且列出的差异能预测下一次会话会犯的错；只总结出正确的废话，算失败。
