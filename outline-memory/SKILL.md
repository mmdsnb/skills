# Outline 共享长期知识

## 何时读

回答或动手前，出现以下情况必须先查 Outline：

- 用户提到「上次 / 之前 / 以前 / 当时 / 为什么这么定」等历史线索；
- 任务涉及项目背景、目标、已确认决策，或机器设备、网络拓扑、外部账号与服务资产；
- 结论依赖个人规则偏好、协作约定或既有 SOP；
- 准备给出方案、诊断或操作建议，且结论依赖用户环境、资产或规则；
- 现有配置或说法与本地残留记录不一致；
- 开始处理某项目，已知有沉淀（不确定就先搜一次实体名）。

纯代码阅读、临时任务、与长期事实无关的对话不触发。

## 何时写

- 用户要求「沉淀 / 记下来 / 记住 / 归档 / 复盘总结 / 写入知识库」；
- 任务收尾或暂停时出现已验证的配置/决策、用户纠正的旧事实、新资产上线、旧方案下线或可复用 SOP，先一句话提议，用户确认后写入。

只写已确认或实测通过的事实；讨论中的提议、临时进度、密码/私钥/Token 一律不写。

## 路由

长期事实一律写 Outline，本地不存事实副本；服务不可用或指令冲突时明确报错，不静默降级。

仅在本项目生效的工程约定（构建/测试/代码风格、目录规范）写项目根 `AGENTS.md`；跨项目长期事实写 Outline。两类内容不互相复制。

## 命令

将 `<skill_dir>` 替换为本技能实际绝对目录：

```sh
uv run --script "<skill_dir>/scripts/outline.py" <命令>
```

| 命令 | 用途 |
|---|---|
| `collections` | 列出可见集合 |
| `tree <collection_id>` | 查看集合目录树 |
| `search "关键词" [--collection <id>]` | 搜索；缺省跨集合 |
| `read <document_id>` | 读取全文与 revision |
| `edit <document_id> --revision <rev> --file -` | 定点替换已有内容（stdin JSON） |
| `update <document_id> --revision <rev> --file -` | 整篇替换（重建文档时用） |
| `rename <document_id> --title "新标题" --revision <rev>` | 修改文档标题 |
| `create "标题" --parent <id> --file -` | 新建实体文档 |
| `append <document_id> [--revision <rev>] --file -` | 仅追加新章节 |
| `create-collection "名称" --description "说明"` | 仅用户授权初始化时 |

- `collections` / `search` 支持 `--limit N --offset N`（默认 25 / 10）。
- `edit` 的 stdin 是 JSON：`{"find": "原文片段", "new": "替换内容"}`。`find` 必须与正文精确匹配（含换行），服务端只替换第一处；匹配不到会报错，不会误写。
- `edit` / `update` / `rename` 必须带 `--revision`（`read` 返回的 `data.revision`）；revision 过期返回 409，重新 `read` 后再改。
- 正文用 stdin（`--file -`）或 `--file <路径>` 传入，不用 `--text` 拼接长文本。
- 输出 JSON：`ok` 成败，`data` 数据；正文在 `data.text`，revision 在 `data.revision`；退出码 0 成功 / 1 调用错误 / 2 参数错误 / 130 中断。

## 读取（先查后答）

1. 先全局 `search "关键词"`（省略 `--collection`），用实体名、别名、项目名、主机名或服务名，换 2–3 组关键词重试；
2. 命中过多或需确认归属时，用 `collections` 定位集合、`tree` 查看层级，再 `search --collection <id>` 精确检索；
3. `search` 分页未读完（`total > offset + limit`）且前序结果相关时，先翻页；
4. 命中后必须 `read` 全文，不只看搜索摘要。

回答规则：

- 引用记录时给出文档标题、urlId/URL 与 `updatedAt`，区分库中记录与本次实测；
- 回答开头注明依据：「据 Outline：<标题>」或「Outline 无记录」；
- 检索无命中时明确说明「Outline 无相关记录」，不用本地残留冒充；
- 文档与实测冲突：以实测为准，并按写入规则更新文档；
- 只读命中的实体文档与正文明确链接的关联文档，不批量拉取整个集合；
- 遇到仍按「修订块」记录的历史文档：以文末最新修订为准，下次写入时顺手整理为当前结论。

## 写入（改原文，不堆流水）

1. 定位：全局 `search` → `tree` 确认实体；已有同实体文档先 `read` 全文，记下 `data.revision`。
2. 已有相关事实：用 `edit` 覆盖旧值。一次 `edit` 改一处；连续修改时使用上一次返回的 `data.revision`。
3. 无相关事实：`create` 新建实体文档；只给已有文档补充新章节时才用 `append`。
4. 只把已验证的事实写进正文；未验证内容放入「待验证」区。
5. 不写过程叙事、废弃值、密码/私钥/Token；旧值直接覆盖，历史由 Outline 版本记录保留。
6. 409 冲突：重新 `read` 获取最新 revision，再重新 `edit`，不盲目重发。
7. 写入成功后回报文档标题与链接。

## 主动沉淀（提议—确认）

触发：任务收尾或暂停时出现以下任一事实，主动评估是否沉淀：用户拍板的决策或方案、用户纠正的既有记录、新设备/服务/账号验证通过、已沉淀方案被证伪或下线、同类 SOP 反复出现、任务复盘中可复用的经验。

价值门：以下五条全部满足才提议，否则沉默：

- 长期性：半年后仍有效；临时进度、一次性动作不写；
- 可复用：下次同类场景可直接使用；
- 已确认：用户拍板或实测验证通过；讨论中的提议不写；
- 非重复：`search` / `read` 后无等价事实；
- 非敏感：不含密码、私钥、Token 等凭据。

动作：

- 用一句话说明「记什么、写到哪」；
- 用户确认后按写入流程执行；明确授权当次可直接写；
- 每个任务最多提议一次，用户拒绝后本会话不再提；
- 写入成功后回报文档标题与链接。

## 信息架构

优先沿用已有集合（如 Personal / Work），按项目归属或上下文匹配，边界模糊时询问用户，严禁跨集合混写。每个集合用十进制编号的一级分类，实体作为二级文档，二级下不再建三级：

```text
├── 10 事项与目标（项目背景、长期目标、已确认决策）
├── 20 环境与资产（机器设备、网络拓扑、外部账号与服务）
├── 30 领域与知识（专业概念、资料、经验复盘）
└── 40 规则与偏好（个人习惯、协作约定、SOP）
```

一客观实体一文档：以具体服务器、组件、系统、项目或独立概念为粒度，把该实体的配置、变更与排错收敛到同一文档，不按单次事件、日期或 Agent 拆分。跨主题用链接关联，不复制正文。

## 文档格式

实体文档正文只放当前有效结论：

```markdown
- 范围：实体与适用边界
- 关键事实：
  - <键>：<当前值>
  - <键>：<当前值>
- 依据：<验证方式与日期，可选>
- 待验证：<尚未确认的内容，无则省略>
```

- 一行一条事实，改一条只动那一行；
- 直接写完整当前值，不写「同上」或差异对比；
- 被替换的值不保留；需要追溯时看 Outline 版本历史。

## 异常

- 写入超时或中断：先 `search` / `read` 确认是否已落库，再决定重试；
- 409：重新 `read` 获取最新 revision 后重试；
- 限流：按提示等待，不盲目重发；
- 服务不可用：明确报错并停止，不写回本地。
